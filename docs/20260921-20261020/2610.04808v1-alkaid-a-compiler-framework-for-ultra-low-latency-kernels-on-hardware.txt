Abstract —Ultra-low-latency machine learning and data pro-cessing pipelines operating on the sub-microsecond level often contain static dataflow kernels that require fine-grained bitwidth control, arithmetic optimization, and fast hardware performance estimation. This works introduce Alkaid, a free and open source domain specific compiler that translates sub-microsecond latency dataflow kernels into platform agnostic Register Transfer Level (RTL) or High-Level Synthesis (HLS)-ready code in seconds. Alkaid targets ultra-low-latency ML pipelines, especially those addressed by existing ML-to-hardware flows such as hls4ml ,while also supporting the surrounding pre-processing, post-processing, and control logic. At its core, Alkaid uses an arithmetic centric intermediate representation, Alkaid Low-level IR (ALIR), to preserve fixed-point semantics, heterogeneous bitwidths, and operation level structure for optimization and code generation. Alkaid further provides comprehensive hardware-aware optimization passes and an interpretable white-box an-alytical performance model for rapid design space exploration without synthesis in the loop. Across representative ML work-loads, including MLPs, GNNs, and transformers, Alkaid achieves 20-30% lower LUT usage than the best prior flows for bit-exact equivalent designs, with up to 40% lower latency in some cases. Beyond typical neural networks, Alkaid achieves comparable performance to the state-of-the-art method for synthesizing boosted decision trees, while also enabling the implementation and integration of non-ML kernels such as sorting networks and histograms. 

I. I NTRODUCTION 

FPGAs are an attractive platform for sub-microsecond, ultra-low-latency computing, especially in domains such as real-time scientific instrumentation [1] and edge intelligence. In these applications, the target computation is often a static dataflow kernel whose graph structure, tensor shapes, and data types are known at compile time. Examples include low-latency machine learning inference kernels and the surround-ing data-processing logic used in Level-1 trigger pipelines at the Large Hadron Collider (LHC). Unlike throughput oriented accelerators, these kernels often target sub-microsecond la-tency, where small changes in bitwidth or arithmetic structure can directly affect both resource usage and timing. Existing ML-to-hardware frameworks such as hls4ml [1] and FINN [2] have shown that neural network models can be translated into efficient low-latency hardware. However, these tools are organized around coarse grained neural network layers with predefined templates. While this makes them effective for supported models, they are less flexible when new ML architectures introduce operators outside the predefined library [1], or when the full application kernel includes cus-tom pre/post-processing operations like tensor arrangement, selection, sorting, or control logic. To address this gap, we present A Library for Kernel Accelerator Implemented on Device ( Alkaid ), a free and open source domain specific compiler framework 1 for low-latency static dataflow kernels. Alkaid translates Python/NumPy descriptions and machine-learning frontend models into Alkaid Low-level IR (ALIR), an arithmetic-centric static single-assignment intermediate rep-resentation. ALIR preserves fixed-point semantics, heteroge-neous bitwidths, and operation-level dependencies throughout tracing, optimization, performance modeling, and code gen-eration. In addition, Alkaid lowers the optimized ALIR into platform agnostic Register Transfer Level (RTL) or High-Level Synthesis (HLS)-ready code. It also provides an interpretable white-box analytical performance model that estimates area and combinational latency from the optimized IR, enabling rapid design-space exploration without invoking synthesis in the loop. Although our evaluation uses FPGA backend tools, the generated RTL is not tied to a specific FPGA vendor and can be integrated into downstream hardware design flows. To the best of our knowledge, Alkaid is the best-performing compiler framework for sub-microsecond dataflow, and the first one providing an accurate, white-box analytical perfor-mance modeling. Existing ML-to-hardware frameworks such as hls4ml [1], 

chisel4ml [3], FINN [2] and fpgaConvNet [4] have shown that neural networks can be translated into efficient FPGA implementations. Other frameworks, such as TreeLUT [5], Conifer [6], and FwX [7], [8], have explored the implementa-tion of decision trees and tree ensembles on FPGAs. However, these frameworks are coarse-grained template-based, making it difficult to implement new layers, which requires sufficient hardware knowledge to manually implement the corresponding layer in either RTL or HLS. More broadly, compiler infrastructures such as Dyna-matic [9], Calyx [10], CIRCT [11], and XLS [12] reflect the growing interest in compiler-based procedural hardware generation. In parallel, frameworks such as DnnWeaver [13], FPGAConvNet [4], ScaleHLS [14], HIDA [15], POM [16], Allo [17], and Stream-HLS [18] have explored automated HLS generation from affine or multi-kernel programs. How-ever, these frameworks are not directly comparable to the proposed framework as their target applications operate at latencies that are orders of magnitude higher than the sub-microsecond regime targeted by Alkaid, where frameworks such as hls4ml [1] and FINN [2] dominate. III. D ESIGN AND ARCHITECTURE 

Alkaid is a domain-specific, kernel-level compiler that trans-lates static dataflow kernels, or computation graphs whose structure and data types are fully determined at compile time, into platform-agnostic RTL or HLS code. To lower the barrier for defining such kernels, Alkaid provides a symbolic tracing frontend based on Python and NumPy: the user “replays” the kernel’s execution on a symbolic tensor provided by the framework using native arithmetic and NumPy operations, and the framework traces the executed operations to construct the corresponding IR. After the IR is generated, it can be optimized with a set of built-in passes, or the user may define custom transformations for specific applications. RTL or HLS code is then generated from the IR with a code generator, which can be used for direct synthesis or as a template for further manual optimizations. The overall architecture of Alkaid is illustrated in Figure 1. 

A. Intermediate Representation and Optimizations 1) ALIR: ALIR, the intermediate representation of Alkaid, is an instruction-based, low-level SSA static dataflow IR tailored for DSP-heavy kernels. While many existing IRs are expressive enough to represent our kernels, ALIR is designed to serve not only as a functional representation of compu-tation, but also as a direct optimization and code-generation substrate for low-latency hardware. The key design choice is that ALIR is arithmetic-centric : all operations are natively defined on fixed-point numbers with arbitrary bitwidths, and the bit-extensions or concatenations required when operating between values of different bitwidths are implicit in the operation semantics rather than explicit IR instructions. By preserving the arithmetic structure instead of lowering to explicit bit-manipulation, ALIR enables optimizations, such as affine-arithmetic-based interval propagation for bitwidth minimization, that would be significantly more convoluted in a bitvector-centric IR like the XLS IR. ALIR is partly inspired by Distributed Arithmetic Instruc-tion Set (DAIS) used in da4ml [19], but the two serve different purposes. DAIS was mainly introduced for distributed arith-metic, with minimal extensions for supporting the inference of specific neural networks. On the other hand, ALIR is designed as a more general arithmetic-centric IR, covering a wider range of static dataflow kernels beyond DA-style linear operators. This includes comparison, selection, lookup, and bitwise operations, while still preserving explicit SSA de-pendencies, fixed-point semantics, and heterogeneous bitwidth support. As a result, ALIR retains the low-level arithmetic transparency of DAIS, while providing a compiler abstraction better suited to Alkaid’s end-to-end optimizations and direct RTL/HLS generation for a broader range of applications. Currently, ALIR implements only 13 low-level operations that have been found to sufficiently cover all operations in the dataflow kernels we have encountered in our target applica-tions, including basic arithmetic operations (neural networks), comparison and selection operations (e.g., sorting networks or decision trees), and boolean operations (e.g., logic-gate networks or generic conditional switches). Due to the low-level nature of the IR, we split optimizations into both the symbolic tracing stage and the traditional IR stage. Optimizations that are local, such as the da4ml optimiza-tion for CMVM operations, or optimizations requiring only information from past operations, such as the affine-arithmetic-based interval estimation and some constant folding/propa-gation, are performed during the symbolic tracing stage as the IR is being constructed. Optimizations requiring a global view of the IR, such as expression canonicalization, common sub-expression elimination, dead/null operation elimination, and further constant folding after these optimizations, are performed iteratively after the IR is constructed. This way, we can maximize the optimization opportunities while minimizing the number of iterations required for global optimizations. 

B. Performance Model 

After these optimizations, the IR closely reflects the post-technology-mapping physical design, enabling a white-box an-alytical model to estimate area and latency without synthesis. For each IR operation, we combine first-principles analysis, such as LUT pin counting, with empirical fitting from micro-benchmarks to estimate its LUT cost and combinational delay. Unlike the machine learning based surrogate models used in hls4ml [20], [21], this analytical approach is directly derived from the IR structure and the underlying hardware implemen-tation, making it interpretable and straightforward to adapt to different target platforms or synthesis tools by adjusting the model parameters. The evaluation of the performance model typically completes in under a second per kernel, which we consider negligible within a typical development cycle. C. Symbolic Tracing Frontend 

The symbolic tracing frontend is Alkaid’s primary frontend, allowing users to define dataflow kernels using native Python and numpy operations on framework-provided symbolic ten-sors. It is designed to be bit-exact: operations on symbolic ten-sors match those implemented in hardware. Intermediate bit-growth is tracked using affine arithmetic where possible, with interval arithmetic as a fallback. Therefore, no implicit quanti-zation is applied; users must explicitly use properly quantized operations and weights, otherwise the generated firmware may become unsynthesizable due to excessive intermediate value sizes. In addition, this frontend also underpins higher-level frontends for machine-learning frameworks. For Keras and PyTorch models, Alkaid traces execution on symbolic tensors for most native operations, while framework-specific plugins define how special layers or operators map to NumPy-based symbolic operations. For other frameworks, Alkaid provides a generic interface for developers to define the full symbolic execution flow. The plugin system decouples compiler infrastructure from frontend development, allowing each frontend to evolve in-dependently and add new operators within its own codebase. It also allows subtle framework-specific differences, such as padding semantics or quantized lookup behavior, to be repre-sented through different symbolic mappings without forcing compromises in the backend. 

1) Layer/Operation Plugin: Currently, Alkaid natively sup-ports the Keras and PyTorch frontends for most of the el-ementary operations. However, since the symbolic tracing frontend does not perform implicit quantization, the models will need to be explicitly quantized before being fed into the framework. In practice, we expect these blocks to be used in conjunction with third-party libraries providing the mapping of their quantization schemes to the symbolic tracing frontend. Currently, plugins for the HGQ [22], PQuantML [23], and torchlogix [24] are implemented with the Keras and Torch frontends. 

2) Framework-wise Plugin: When the frontend model is provided by another framework, such as XGBoost [25] or hls4ml [1], developers may define a plugin describing how the model should be executed on the symbolic tensors. This plugin is generally more flexible than the prior operation/layer plugin, while also requiring more effort to implement. For instance, the XGBoost plugin would allow the user to configure how the leaf values are mapped/quantized to fixed-point numbers, and if the tree is to be implemented as a lookup-table or muxes. The hls4ml plugin allows the conversion of an optimized hls4ml model targeting the Vitis HLS backend into ALIR, which can then be further lowered into RTL or HLS code with the Alkaid code generator and remains bit-exact to the original hls4ml model. 

D. Code Generation Backend 

Currently, Alkaid provides two code generation backends: a platform-agnostic RTL generator, whose output can be used for direct synthesis or as a template for further manual integration, and an HLS generator targeting Vitis HLS and oneAPI DPC++. Alkaid also provides an IR-to-IR translator layer that emits XLS IR from the optimized ALIR via the C binding to libxls, enabling integration with XLS-based flows. E. hls4ml Integration 

While Alkaid is mainly designed as a standalone tool, an alternative to hls4ml , for users who are already familiar with hls4ml, or have existing models defined in hls4ml, Alkaid provides seamless integration with hls4ml to allow users to benefit from Alkaid’s broader operator support and faster development cycle while retaining the familiar hls4ml interface. In particular, for the hls4ml/Keras frontend, when an unsupported layer is encountered during hls4ml’s parsing, the hls4ml plugin for Alkaid will be triggered to convert the unsupported layer into ALIR. The ALIR will then be converted into HLS code with Alkaid’s code generator and inlined into the generated HLS code from hls4ml, which can then be fed into the synthesis tool for downstream processing. IV. E VALUATION 

Unless otherwise stated, all Alkaid results are obtained using Vivado 2025.1 targeting the UltraScale+ VU13P FPGA (xcvu13p-flga2577-2-e ), based on out-of-context post-routing reports. Following prior work, we report latency as the number of cycles at the maximum achievable clock frequency (Fmax ). All designs are registered at both input and output ports to cover all combinational paths, and the cycle latency is measured as the number of registered combinational stages. In all evaluated neural network designs, Alkaid generates bit-exact RTL designs compared to the original designs, while reducing the LUT usage by 20-30% and latency by up to 40% compared to da4ml or hls4ml+da4ml implementations. Comparing to hls4ml standalone, it achieves 50-70% LUT reduction and > 99% DSP reduction without the da4ml 

algorithm optimization. Compared to TreeLUT for decision tree based models, Alkaid achieves comparable efficiency in LUT usage and latency. 

A. Performance Modeling 

To evaluate the accuracy of the performance model, we compare the estimation from the performance model with the post-routing results from Vivado 2025.1 for a large set of machine learning models, including the multi-layer perceptron (MLP), static graph neural networks (GNN), JEDI-linear [26], TGCNN [27], and transformers. Some non-ML kernels, such as the parallel sorting networks, are also included in the evaluation since they are commonly used in the LHC trigger pipelines. A total of 2,410 designs are evaluated for the performance model, with a wide range of LUT usage from half a thousand to over half a million. We show the correlation plots and the distribution of relative estimation error for both LUT usage and latency in Figure 2. We find that our performance model can achieve an estimation error of < 10% for LUT usage and < 20% for latency compared to the post-routing results from Vivado 2025.1 in general. In both cases, we find other factors, such as the target clock frequency, routing congestion, or even the version of the synthesis tool may lead to a larger variation in the actual area and latency of the generated design, which is not and cannot be captured by the performance model. This appears to be a fundamental limitation shared by any pre-routing analytical model, as even the vendor tools’ own timing estimates degrade significantly under heavy routing congestion. Hence, we consider the estimation error of the performance model to be sufficient for users to quickly iterate on their design and explore the design space before running the synthesis step.

For this study, we consider the models with a maximum of 16 or 32 particles with both the GNN and transformer/linformer architectures. For the decision tree models, we consider the models trained on the same JSC task with the same dataset as well as the MNIST [31] dataset. Since the exact models with the specified accuracy are not provided in the original TreeLUT paper, we fit the decision trees ourselves targeting the same accuracy. The decision trees are then converted into RTL with Alkaid for the evaluation. This results in slightly different models between the two implementations, but we consider the accuracy to be close enough for a meaningful comparison of the perfor-mance and resource usage of the generated designs. For this comparison, it should be noted that the latencies reported for TreeLUT [5] are adjusted due to different evaluation protocols. TreeLUT uses unregistered inputs and outputs with 0.05-0.1 ns external delay, while the latency cycle number is counted by the number of internal registers between the input and output ports. On the other hand, we count the number of cycles in Alkaid with the number of combinational blocks between the registered input and output ports, which has +1 cycle compared to the TreeLUT counting method with the same pipelining. To normalize the latency results, we adjust the latency for TreeLUT to be reported latency + clock period − 0.2 ns, where the clock period is calculated as the inverse of the reported Fmax . The 0.2 ns is the higher estimate derived from the 0.05-0.1 ns delays added by the authors for the unregistered input and output ports, which yields the most favorable adjusted latency for TreeLUT. Since TreeLUT omits the input and output registers, the FF counts cannot be directly compared between the two implementations but are included for completeness. The results for the JSC HLF and JSC PLF tasks are summarized in Tables III and IV, respectively. The results for the decision tree models are summarized in Table V. The MLP, transformer, and Linformer models are converted via the HGQ plugin, while the GNN models are converted via the hls4ml plugin for bit-exactness. The BDT models are converted with the XGBoost plugin with explicit quantization support. For neural network models, we find that Alkaid can gener-ally achieve 20-30% lower LUT usage compared to the designs generated by da4ml or hls4ml with the da4ml plugin. On some designs, the latency could also be reduced by up to 40% compared to the original designs, while maintaining similar latency on others. We attribute the LUT improvement over da4ml to the affine arithmetic based bit-growth tracking, which allows Alkaid to use smaller bit-widths for the intermediate values without causing overflow, while da4ml relies on a more conservative interval arithmetic that leads to larger bit-widths in general. The latency improvement is likely from both the reduced arithmetic complexity and better latency performance modeling, which allows for better path length balancing and more efficient pipelining. Compared to hls4ml without using da4ml for CMVM kernel optimization, Alkaid can achieve significantly lower LUT usage while mostly eliminating DSP usage. For the BDT models, Alkaid achieves equivalent or slightly better accuracy compared to TreeLUT [5] with similar LUT usage and latency after adjusting for the different evaluation protocols. How-ever, the Alkaid designs still outperform the original hls4ml designs with 50 -70% lower LUT usage and > 99% lower DSP usage in general, while simultaneously achieving II=1 compared to hls4ml’s II=2, which is strictly higher throughput with lower resource utilization. Due to the high LUT usage, we observe high routing congestion (level 4-5) for the JEDInet designs, which leads to a significant reduction of Fmax and hence higher latency than the performance model’s estimation. Since some designs span over one SLR and the cross-SLR routing delay is not modeled in the performance model, the pipelining is likely to be less efficient than the estimation as well, which also contributes to the lowered Fmax . Since the original hls4ml designs are not routed, we cannot compare the actual latency of the two implementations. Another advantage of Alkaid over hls4ml, or other HLS-based flows is the significantly faster development cycle enabled by the quick model-to-RTL conversion and accu-rate performance estimation. For the JEDInet models and the transformer/linformer models, the designs generated by hls4ml, with or without the da4ml plugin, require hours to days for a single HLS synthesis. In particular, the JEDInet models require days for HLS and logic synthesis, while the transformer/linformer models could also need more than one day. In contrast, the model-to-RTL conversion with Alkaid takes less than a minute for all of the models shown, and the logic synthesis for the each take no more than 50 minutes. This allows users to iterate on their designs much more efficiently and explore the design space with more freedom.

C. Non-Machine Learning Kernels 

Beyond machine learning models, Alkaid can also be used to convert other types of computation kernels into RTL code as long as they can be expressed in reasonably well-structured Python/NumPy code. For instance, one can create a parallel sorting network with the np.sort or np.argsort 

functions, or a histogram kernel with the np.histogram 

function. We show the latency and resource usage of the generated designs for these kernels in Table VI. We also show an example of how the different NumPy functions can be com-posed in a pythonic way to create a more complex dataflow kernel in Listing 1. In this particular example, the kernel is generated with the inputs being unsigned 8-bit integers, and the generated design will be bit-exact to the description in the Python function, with the intermediate values tracked automatically. To demonstrate support for a backend beyond AMD FPGAs, these non-ML kernels are synthesized with Quartus 25.1 targeting the Altera Agilex 7 FPGA. The sorting and histogram kernels are commonly used in the pre-processing stage of many machine learning models at the LHC, such as for jet constituent ordering and feature extraction or creation for the downstream models. With Alkaid, one can create a unified dataflow graph containing both the machine learning model and the pre-/post-processing steps, and convert the entire graph into an RTL project with a single workflow. V. C ONCLUSION 

We present Alkaid, a domain-specific compiler that trans-lates low latency kernels into platform-agnostic RTL or HLS code. Alkaid combines a Python/NumPy symbolic tracing frontend, an arithmetic-centric IR (ALIR), and a white-box an-alytical performance model for rapid design-space exploration. As a design choice, Alkaid generates stateless pipelined designs similar to XLS functions, and we consider scheduling and orchestration to be an orthogonal step at the higher level. We aim to enable processing element reuse and throughput-area trade-offs for larger models and support more complex dataflow graphs in the future.
