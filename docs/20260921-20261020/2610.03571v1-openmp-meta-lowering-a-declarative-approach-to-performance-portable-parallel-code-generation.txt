## Abstract 

The increasing diversity of parallel hardware challenges ex-isting compilation flows. While OpenMP provides a portable abstraction for shared-memory parallelism, existing com-pilers tightly couple the frontend semantics with fixed low-ering strategies. This design limits performance portability across different runtimes and architectures. In this paper, we present a modular approach to parallel code generation based on the Multi-Level Intermediate Representation (MLIR) framework. Our approach combines an OpenMP frontend with a domain-specific language (DSL) that specifies how OpenMP constructs are lowered for a target. We call this approach OpenMP meta-lowering, treating lowering as a pro-grammable component rather than compiler-specific logic. This design provides explicit control over code outlining, data sharing, and runtime interfacing across diverse tar-gets. We evaluate our approach on PolyBench/C-OMP across general-purpose and embedded multicore targets. Our re-sults show that the proposed method matches the perfor-mance of state-of-the-art compiler toolchains with negligible code-size overhead (< 0.7%). Preserving OpenMP constructs until late lowering stages enables both general-purpose and OpenMP-specific MLIR optimizations. By decoupling low-ering from compiler internals, our approach expresses the same OpenMP subset in 5,182 lines of code, ∼32% fewer than the corresponding lowering code in Clang and ∼76% fewer than in GCC, while supporting the pmsis runtime costs only a few specification lines, enabling rapid support for new runtimes without modifying the compiler.

To address this complexity, high-level parallel program-ming models have been introduced to allow developers to ex-press parallelism independently of the underlying hardware. Unlike previous MLIR-based approaches, which rely on fixed lowering pipelines [24] or imperative transformations implemented through compiler passes and pattern rewrites [19, 20], our methodology treats lowering as a declarative, runtime-parametric abstraction. 2.1 MLIR-Based OpenMP Compilation 

MLIR [14] is a compiler infrastructure designed to support multiple levels of abstraction within a single compilation framework. Rather than lowering source code directly to a low-level representation, MLIR organizes programs into 

dialects , each providing domain-specific operations, types, and transformations. This design enables high-level program information to be preserved throughout compilation and progressively lowered toward machine code. Our work builds on ClangIR (CIR) [22], a high-level MLIR dialect for C/C++. CIR represents source-language constructs such as functions, loops, variables, and control-flow struc-tures while retaining information that is typically lost during early lowering to LLVM IR. The CIR compilation flow in-tegrates with the broader MLIR ecosystem, allowing CIR operations to coexist with operations from other dialects. OpenMP support in MLIR is provided through the ded-icated omp dialect, which models OpenMP directives and clauses. Since both CIR and OpenMP are represented as MLIR dialects, parallel constructs remain explicit alongside the surrounding C/C++ code throughout most of the compi-lation process. This separation between high-level parallel semantics and low-level code generation enables transforma-tions and optimizations to be applied before runtime-specific lowering decisions are introduced. 

2.2 OpenMP Lowering 

OpenMP compilation requires translating high-level parallel constructs into runtime-specific implementations. This pro-cess typically involves three categories of transformations. First, function outlining extracts the body of a parallel region into a separate function. Second, control-flow restructuring 

rewrites work-sharing constructs, such as parallel loops, into forms compatible with the scheduling mechanisms provided by the target runtime. Third, runtime call emission introduces calls that implement thread creation, synchronization, and work distribution. In current MLIR-based toolchains, these transformations are implemented through OpenMPIRBuilder and are tightly coupled to the ABI of a specific runtime, namely libomp .For example, OpenMP constructs are lowered into runtime-specific calls such as __kmpc_fork_call and loop schedul-ing routines whose interfaces are embedded directly into the

lowering implementation. Consequently, supporting alter-native runtimes requires modifying compiler-internal code rather than simply changing the runtime description. This tight coupling between OpenMP semantics and runtime-specific lowering motivates the approach proposed in this paper. Instead of hardwiring runtime behavior into compiler passes, we externalize lowering decisions into a declarative specification that the compiler infrastructure can interpret and adapt to different runtime environments. A DSL specification defines which runtime calls to emit and which code-generation strategy to apply for each construct; the proposed compilation pipeline applies the actual changes. 

## 3 Methodology 

In this section, we present our OpenMP meta-lowering ap-proach. A DSL specification declares, for each OpenMP con-struct, how it is realized on a target runtime: the runtime calls to emit, their position relative to the construct body, and the handling of the body itself. Section 3.1 describes what a specification can express and Section 3.2 formalizes its grammar; Section 3.3 describes the three-phase MLIR pipeline that performs the lowering, and Section 3.4 walks through a complete example. The last two subsections state how correctness is checked and which constructs are cur-rently supported. 

3.1 What a specification can express 

A specification outlines how each omp -dialect operation is lowered for a target runtime. It does so in terms of four concepts: 1. The omp -dialect operations that a specification can lower ( omp.parallel , omp.wsloop , etc.). 2. The context variables that each operation exposes, rep-resented by the values of its clauses ( num_threads ,

nowait ). 3. The body-handling modes available to a construct: its body may be outlined into a separate function, restruc-tured as a work-sharing loop, or absent. 4. The structured rewrites that a specification can invoke, each generating a dedicated code pattern. There are no restrictions on the names of functions, which means that a specification can express any construct that re-duces to a sequence of runtime calls associated with one of the body-handling modes. Section 3.6 outlines which OpenMP constructs are currently included in this set.

Runtime and construct declarations. A runtime block may contain local bindings ( let-decl ) and any number of 

construct declarations . Each construct declaration maps an operation of the omp dialect to a set of lowering rules. An optional when guard, expressed as a predicate over the con-struct attributes, allows the same construct to be handled differently depending on runtime conditions. For example, it can be used to differentiate between parallel regions that specify or do not specify a num_threads clause. 

Construct items. A construct declaration consists of a flat list that includes three types of items. A property dec-laration associates a name with an expression, making it available as a symbol during the lowering process. A let dec-laration introduces a constant binding that is valid within the scope of the construct. A block declaration describes the low-ering process in terms of three lifecycle blocks: pre , executed before materializing the construct; invoke , which handles the materialization of the construct’s parallel semantics and may either dispatch an outlined function via call or apply

structured rewrites via emit ; and post , executed after the construct materialization. 

Statements and actions. Within a lifecycle block, each statement either fires unconditionally or is guarded by a 

when /otherwise conditional. The executable unit of a state-ment is an action , of which there are two forms. A call action invokes a function with a list of expressions as arguments, corresponding to the emission of a runtime library call into the lowered IR. An emit action names a structured rewrite supported by the infrastructure, such as thread_bounds or 

loop_body , allowing IR rewrites and runtime calls to be composed declaratively within the same lowering sequence. 

Predicates. Guards on both construct declarations and in-dividual statements are expressed as predicates . The grammar supports conjunction ( and ), disjunction ( or ), and negation (not ), following standard precedence rules from lowest to highest. Atomic predicates can check for the presence of a named attribute using has , compare the attribute value with a reference using == or != , or treat the attribute name as a boolean flag. Parentheses are available for explicit grouping. 

Expressions. Expressions cover the value language used in property bindings, let declarations, and action arguments. An expression can be a function call, a bare identifier refer-ring to a bound attribute or let variable, a string or integer literal, a boolean literal, or a list. Lists allow passing struc-tured data, such as sets of clause names, as arguments to 

call or emit actions. Primitive token types ( IDENT , STRING ,

NUMBER ) are supplied by the lexer and are not expanded further in the grammar. 

3.3 MLIR Lowering Pipeline 

The lowering pipeline consists of three MLIR passes orches-trated by mlir-opt-omp , a custom driver built on top of the standard MlirOptMain entry point. The driver registers the dialects required throughout the pipeline: cir , arith , func ,

llvm , omp , and the custom omp_lower dialect. Two flags control the global lowering configuration: –omp-lower-dsl 

specifies the path to the DSL file containing the runtime declarations, and –omp-lower-runtime selects the target runtime from that file. Dialect legalization is handled trans-parently by the MLIR conversion framework, which verifies that all operations are legal with respect to the registered dialects after each pass. Figure 1 shows the three passes and their integration into the compilation pipeline. 

Pass 1: Annotation ( –omp-to-omp-lower ). The first pass processes the DSL file using a dedicated parser and evaluates the lowering declarations for the selected runtime. For each visited operation, the pass selects the declaration to apply based on the actual values of the clauses: a when 

guarded declaration takes precedence over an unguarded one. When no declaration matches, the pass reports an error. Based on the selected declaration, the pass then attaches the lowering plan to the omp dialect operation, encoded as an additional operation belonging to the custom omp_lower 

dialect. This operation records the target runtime name, the construct identifier, a dictionary of resolved property bind-ings, and three data structures carrying the pre , invoke ,and post action sequences. As a result of this pass, the struc-ture of the omp operations remains unchanged, but they now carry all the necessary meta-level information required by the subsequent passes. 

Pass 2: Outlining ( –omp-outline ). The second pass con-siders the lowering annotations from Pass 1 and realizes the body-handling mode that each construct requires. Where that mode is function outlining (e.g., omp.parallel ), it col-lects the variables crossing the region boundary, extracts the body into a separate function, and rewrites the original site into a dispatch point. The signature of the outlined func-tion and the way captured variables are passed to it are not hardcoded in the pass, but dictated by outline_signature 

and capture_strategy properties of the plan. When using 

by_pointer , each capture is treated as a separate argument in the outlined function; with packed , captures are combined into a single structure allocated at the call site, which defines the env_size and env_align context variables for size and alignment, respectively. For an omp.wsloop , whose body is restructured, the pass computes the iteration range assigned to each thread and rebuilds the loop over that range. 

Pass 3: Plan application ( –omp-lower-plan ). The third pass applies the lowering plan produced in Pass 1 to the out-lined code from Pass 2, materializing the pre , invoke , and 

post action sequences for each construct. For each omp op-eration, the pass first processes the pre actions, inserting the corresponding llvm dialect calls or applying structured rewrites immediately before the construct in the IR. It then processes the invoke actions, which materialize the con-struct at the point where the original omp operation appears. Finally, it processes the post actions, inserting any required teardown or synchronization code immediately after the construct. For each set of actions, call actions are lowered to di-rect llvm.call operations with the resolved function name and argument list. Each argument name resolves to an SSA value in the IR: num_threads and if_clause to operands that the omp operation already carries, body to the function outlined by Pass 2, and env_ptr to the capture structure built at the dispatch site. emit actions are dispatched by name to a registry of standard IR rewrite patterns, each of which pro-duces a fixed sequence of llvm dialect operations, detailed in Section 3.4.

3.5 Well-formedness and semantic preservation 

Specifications are checked at several points: the parser ac-cepts only well-formed programs, and lowering stops on a construct with no matching declaration or on a plan nam-ing an emit keyword or a property value that no pass im-plements. Each pass leaves the IR in a form that the MLIR verifier accepts, so any mismatch between a plan and the code it applies to is detected during compilation. OpenMP semantics (regions, nesting, clauses) are encoded in the omp 

dialect produced by the ClangIR frontend. The three passes transform the program without altering its semantics: the annotation pass attaches information; the outlining pass re-locates a region into a separate function and restructures work-sharing constructs; the plan application pass emits runtime calls and applies structured rewrites. 

3.6 Scope and limitations 

Table 1 lists the constructs and clauses supported by our current implementation. PMSIS covers fewer constructs be-cause the bare-metal cluster runtime lacks a tasking API, which is essential to implement constructs such as task and 

taskwait . However, constructs that are not yet supported can still be expressed. For example, constructs like critical ,which require a sequence of runtime calls around a specific region, simply need a dedicated declaration, as the existing passes already provide the necessary body-handling mode. Constructs like atomic , which require the lowering to be a single instruction instead of a call, will also need an emit keyword added at that level. 

## 4 Results 

In this section, we assess the effectiveness of our approach us-ing three main criteria: performance portability, engineering effort, and integration with the MLIR optimization pipeline. We compare against state-of-the-art compiler toolchains across both general-purpose and embedded platforms, as-sessing parallel speedup, code size, and implementation com-plexity. 

4.1 Experimental setup 

Benchmark suite. We evaluate our approach using the PolyBench/C benchmark suite [31] in its OpenMP-enabled variant (PolyBench/C-OMP). PolyBench is a widely adopted collection of computational kernels representative of numer-ical workloads, including linear algebra, stencil computa-tions, and dynamic programming. We selected this bench-mark suite for our experimental assessment because it offers a diverse set of computational kernels that cover various domains such as linear algebra, stencil computations, and dynamic programming. These benchmarks are also highly representative of modern numerical and machine-learning workloads. Their structured, loop-based design makes them especially suitable for evaluating compiler transformations and parallelization strategies in a controlled and reproducible environment. The suite provides multiple dataset sizes. In our exper-iments, we use the large configuration on the general-purpose platform to expose sufficient parallelism and stress both computation and memory subsystems. For the PULP platform, we use the mini dataset instead, as this architecture provides limited on-chip memory. Tasking is supported on both general-purpose runtimes, where we validated it for functional correctness; the PULP cluster runtime does not provide it. For the performance eval-uation, we considered a single benchmark suite executable on every target. 

General-purpose platform. Experiments targeting general-purpose runtimes were conducted on an Intel ®

Core™ i7-10700K CPU operating at 3.80 GHz. This processor features 8 physical cores with simultaneous multithreading (SMT), for a total of 16 hardware threads. The system is equipped with 32 GB of DDR4 main memory. The memory hierarchy follows a typical multi-level cache organization. Each core has private L1 instruction and data caches (32 KB each) and a private 256 KB L2 cache. All cores share a unified last-level cache (L3) of 16 MB. 

PULP platform. For the embedded evaluation, we target a GAP8 [11] board, which is a physical embodiment of the PULP architecture. The GAP8 system-on-chip integrates a heterogeneous multicore architecture composed of a fabric controller (FC) and a cluster of 8 RISC-V cores dedicated to parallel computation. The memory hierarchy is explicitly managed with the aim of optimizing energy efficiency. The cluster features a 64 KB shared L1 scratchpad memory that is software-managed and provides low-latency access for all cores. This memory is backed by a 512 KB L2 scratchpad shared with the FC. Data transfers between L2 and L1 are orchestrated explicitly via a Direct Memory Access (DMA) engine. 

Compiler toolchains. On the general-purpose platform, we use two compiler toolchains: GCC 12.3.0 (binary release) and LLVM 23.0.0 (git development branch). The LLVM fron-tend has been extended to support the lowering of omp dialect operations that are not yet handled by the mainstream CIR pipeline.

Because DSL-driven low-ering rewrites only the omp constructs and the CIR is left untouched, any existing or future CIR transformation ap-plies unchanged; and the omp operations are still in the IR, so transformations that depend on OpenMP structure become possible as well. After lowering, the resulting LLVM IR still benefits from the standard LLVM optimization pipeline. 

A general-purpose transformation. We implemented a custom loop unrolling pass in the CIR dialect. It operates directly on cir.for constructs and unrolls innermost loops by a factor of two, analyzing loop bounds statically and drop-ping the residual iteration when the trip count is provably even. This optimization is particularly effective on the GAP8 platform because it increases instruction-level parallelism and hides the single-cycle latency of the L1 scratchpad, im-proving overall execution efficiency. Moreover, eliminating redundant condition checks in the inner loops significantly reduces the total execution cycles. Figure 8 shows the speedup increment achieved by en-abling this optimization. Across ten applications, loop un-rolling yields an average improvement of approximately 4.6%, ranging from 6.8% for correlation down to 1.0% for fdtd-2d. The remaining applications in the benchmark suite are only marginally affected by loop unrolling. 

An OpenMP-specific transformation. The implicit bar-rier that closes a work-sharing loop is redundant when the loop is the last statement of its parallel region, since the following join point already waits for every thread. We im-plemented a pass on the omp dialect that removes such barri-ers, along with explicit omp.barrier operations that open a region, close it, or immediately follow another synchroniza-tion point. Traditional compilers apply this elision: Clang only when the loop is written as a combined parallel for ,GCC also when the parallel region and the for loop are separate. Across the PolyBench suite, our pipeline emits 59 team-barrier calls without the pass and 26 with it. On the same kernels, Clang and GCC emit 45 and 28 barriers, re-spectively. Compared with the previous transformation, the performance impact on the GAP8 platform is minimal: an overall saving of 0.037%, with 22 of 30 kernels improving and a per-kernel range of −0.16% to +1.12% ( trisolv ). These values are small because the barrier cost on the GAP8 cluster is very low (around 20 cycles) and the kernels are simple, but more complex applications can benefit significantly from this optimization. The few regressions are due to code layout effects rather than the cost of the transformation: removing a call shifts the surrounding code, changing how it maps to the shared instruction cache in the cluster. These experiments highlight the importance of optimizing before lowering. By leveraging MLIR, our framework enables a flexible compilation strategy where high-level transforma-tions and backend optimizations complement each other. 

## 5 Related Work 

Prior work relevant to this paper lies at the intersection of OpenMP runtime support, compiler intermediate represen-tations for parallelism, and MLIR-based infrastructures. 

OpenMP compiler and runtime implementations. Asubstantial body of research focuses on compiler toolchains and runtime systems that efficiently realize the OpenMP execution model on specific platforms. Mainstream ecosys-tems such as GCC and LLVM provide mature implementa-tions through tightly integrated runtime libraries, notably 

libgomp [12] and libomp [23]. In these systems, the lower-ing of OpenMP constructs is tightly coupled with compiler-specific code-generation paths and runtime-specific ABIs. While this design enables high efficiency, it limits portabil-ity across runtimes and architectures. This coupling is even more pronounced in embedded and ultra-low-power sys-tems, where runtime support is often highly specialized for the target hardware. Several works [3, 32, 35] demonstrate OpenMP support on embedded targets through custom im-plementations, while Agathos et al. [1] go a step further by proposing a compiler-assisted adaptive runtime organization for embedded multicores. Although these approaches high-light the importance of compiler–runtime co-design, they retain the assumption that lowering is a compiler-internal, target-specific mechanism. 

Decoupling lowering from compiler and runtime. Ear-lier research works have loosened that coupling in differ-ent ways. Mercurium [2] specifies the transformation of OpenMP directives through code templates, written in the source language. ROSE [17] translates OpenMP into calls to XOMP, a common runtime library that needs to be imple-mented on top of each target library. OpenUH [16] lowers OpenMP within Open64’s IR and can re-emit the result as  

> 11 CGO 2027, March 2027, Salt Lake City, UT, USA Luca Parigi and Giuseppe Tagliavini

source code, making the translation portable. Our approach specifies lowering rules applied directly to the constructs rather than using a template for instantiation or translating to a common library. The calls generated by these rules di-rectly invoke the target runtime, eliminating the need for any additional layers specific to each runtime. Additionally, both general-purpose and OpenMP-aware transformations can be applied to the IR before lowering. 

Intermediate representations for parallel semantics. 

Another line of work argues that parallel semantics should remain explicit in the compiler intermediate representation, rather than being lowered prematurely into runtime calls. Tapir [33] extends LLVM IR with explicit fork-join constructs, enabling optimization of task-parallel code prior to runtime mapping. Similarly, OpenMP-aware compiler optimizations operate on enriched intermediate representations that pre-serve OpenMP semantics, allowing analyses and transfor-mations that would otherwise be obscured by early lower-ing [8]. More generally, unified parallel intermediate rep-resentations such as UPIR [34] aim to capture parallel se-mantics across multiple programming models in a common abstraction. While these approaches emphasize preserving parallel structure for optimization and analysis, they focus on representation and transformation rather than on making the lowering itself programmable. 

MLIR-based OpenMP compilation and declarative specification. MLIR provides a structured OpenMP compi-lation flow in which directives are represented in the omp 

dialect and progressively lowered through the MLIR/LLVM stack [18, 21]. While this design preserves high-level seman-tics and enables composition with other dialects, the final lowering remains tied to a specific runtime ABI through compiler-internal translation logic. MLIR also provides mechanisms for declaratively spec-ifying transformations. DRR [20] and PDLL [19] express local IR rewrites, while the MLIR Transform dialect [25] lets performance engineers script fine-grained optimization sequences such as tiling, unrolling, and vectorization over the IR. These approaches are declarative and IR-native, but domain-agnostic: they focus on which transformations are applied to a program rather than on how parallel constructs are mapped to a runtime, and they have no vocabulary for OpenMP lowering concepts, so outlining, capture-struct lay-out, and if-clause serialization fall back to native rewrites. Recent work has demonstrated that multi-level IRs can en-able retargetable compilation flows and facilitate the integra-tion of domain-specific optimizations across abstraction lev-els [9, 10, 24]. However, the lowering process itself remains encoded in compiler passes or transformation pipelines, and is not exposed as a programmable abstraction. 

Imperative and structure-preserving alternatives. Arelated line of work modularizes OpenMP lowering or pre-serves high-level program structure, but does so imperatively rather than declaratively. The OpenMPIRBuilder, which un-derlies the MLIR OpenMP translation infrastructure [18, 21], factors runtime-call emission into helper functions shared across frontends, yet fixes the target runtime in its transla-tion logic: retargeting requires modifying the builder itself. Our DSL expresses the same mapping declaratively rather than relying on compiler-internal code. Polygeist [26] raises C/C++ into structured MLIR (the scf and affine dialects) to expose programs to polyhedral and affine optimization. It shares the philosophy of preserving high-level structure before lowering, but targets loop-level optimization rather than runtime abstraction: the lowering itself remains a fixed compiler-internal process. 

Positioning of this work. Our work builds on existing foundations but addresses a different problem. Instead of introducing a new representation or transformation mecha-nism, we elevate OpenMP lowering to a first-class, declara-tive, and runtime-agnostic abstraction. Unlike previous ap-proaches that either specialize runtime implementations, pre-serve parallel semantics for optimization, or provide struc-tured compilation infrastructures, our method allows the same OpenMP representation to be reconfigured for differ-ent runtimes via a configurable lowering specification, all without modifying the compiler internals. 

## 6 Conclusion 

This paper introduces a meta-level declarative approach to OpenMP lowering that rethinks the traditional compilation pipeline as a programmable, runtime-agnostic process. Our framework replaces monolithic lowering with a configurable specification: even with the flexibility of MLIR, the tradi-tional lowering process remains encoded in compiler passes, whereas our approach expresses it through an external DSL. Our evaluation shows that this flexibility comes at no cost in performance or code size, while the lowering pipeline takes 5,182 lines of code, ∼32% less than the corresponding code in Clang and ∼76% less than in GCC. The current implementation supports a subset of OpenMP sufficient for different application domains; supporting ad-ditional features, such as offloading and more complex syn-chronization patterns, is a natural evolution. More broadly, the declarative lowering paradigm introduced in this pa-per can be generalized to other programming models (e.g., SYCL) and to different scenarios, such as describing the code transformations required to map code to a custom acceler-ator. This approach would enable a new class of compiler frameworks in which lowering strategies are expressed at a meta-level and adapted to diverse execution contexts.
