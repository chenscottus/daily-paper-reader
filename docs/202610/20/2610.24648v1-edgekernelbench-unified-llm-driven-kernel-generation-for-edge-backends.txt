## ABSTRACT 

Recent works show that LLMs can generate kernels with strong performance on server GPUs. Edge deployment presents distinct challenges because the hardware is heterogeneous, the software stacks are fragmented, and the resource budgets are tight. LLM kernel generation across diverse edge backends has yet to be studied systematically. We introduce EdgeKernelBench , which combines a unified IR deployment framework with a hierarchical benchmark for edge workloads. The unified IR captures reusable computation, scheduling, and memory decisions and connects to each target backend through a compiler interface. The benchmark spans progressively larger program scopes, from individual operators to compact model graphs, across representative edge application domains. We instantiate the design with TVM as a reference compiler and validate it across heterogeneous edge backends. With a single generation attempt, the best model achieves 64.5% Correct@1 but only 25.5% Fast@1 .0. This gap shows that functional correctness does not consistently translate into performance gains. We therefore introduce the Layered Edge Kernel Agent (LEKA) , which organizes optimization through a layered IR. On the agent evaluation subset, LEKA achieves 43.5% Fast@1 .0,compared with 13.0% for direct generation and 26.1% for Claude Code. LEKA and Claude Code use the same base model and optimization budget. Together, EdgeKernelBench and LEKA support unified evaluation and layered optimization of kernels generated by LLMs across edge backends. 

## 1 INTRODUCTION 

Growing demand for low latency, reduced network reliance, and local data processing drives model deployment on edge devices (Zhou et al., 2019; Xu et al., 2021). Yet rapidly evolving models must run across diverse runtimes and hardware backends. Deployment systems continue improving infer-ence efficiency across platforms (NVIDIA, 2026; Jiang et al., 2020; Nachin et al., 2026). Still, new operators and backends often require custom kernels. The need to manually implement, validate, and maintain high-performance operators remains a persistent bottleneck in edge deployment. Large language models can now generate executable code from natural language descriptions (Chen et al., 2021; Li et al., 2022). Recent works apply this capability to high-performance kernel gen-eration (Ouyang et al., 2025; Li et al., 2025a; Lin et al., 2026). However, most of this work still targets server GPUs. There are three major problems that prevent these methods from being used to generate kernels for edge devices, as illustrated in Figure 1. 

(1) Edge hardware and software ecosystems are highly fragmented. Server kernel generation usually targets a small set of mainstream accelerators supported by mature software stacks. Edge de-vices span heterogeneous processors, vendor runtimes, and deployment engines. Generating native programs directly ties reusable computation and scheduling knowledge to the languages, interfaces, and legality rules of individual backends. Supporting a new backend therefore requires the model to adapt to another programming and deployment environment, which limits transfer across devices. 

(2) Edge kernel generation has a different optimization objective from server kernel genera-tion. Server kernels often run on accelerators with ample dedicated memory, allowing optimization to focus primarily on execution speed. Edge workloads share compute and memory with the rest of the system, and memory capacity can determine whether a model is deployable. Edge kernel generation must therefore optimize performance and memory jointly within a fixed resource budget.

(3) Existing benchmarks do not fully capture the requirements of edge kernel generation. Ker-nelBench and related studies mainly target server GPUs (Ouyang et al., 2025; Li et al., 2025a), while MobileKernelBench extends evaluation to mobile devices (Zou et al., 2026). Its public tasks consist mainly of individual operators and their attribute variants. Such tasks assess basic code generation, but not cross-operator optimization or graph-level resource planning in edge deployments. To address these problems, we introduce EdgeKernelBench . It combines a unified deployment framework with a hierarchical benchmark for edge workloads. The LLM does not produce a separate native program for each backend. The LLM expresses optimization choices for the target device in a unified intermediate representation, or IR. A deterministic backend adapter then lowers the program to the target backend in stages. This separation isolates reusable computation and knowledge from interfaces that are specific to each backend. EdgeKernelBench also places scheduling and memory decisions in the same optimization space. The model can reuse optimization knowledge across backends while balancing execution performance and memory cost under deployment constraints. All EdgeKernelBench tasks are PyTorch reference programs with traceable provenance (Paszke et al., 2019). The tasks are organized along two orthogonal axes, compositional complexity and application domain. The complexity axis contains three levels named Basic Compute Patterns , Com-posed Operator Graphs , and Compact Model Graphs . The application domains cover Mobile and Personal Intelligence, Embodied Robotics, and Smart AIoT. Separating these axes enables targeted evaluation of optimization capabilities across edge deployment settings. To test the feasibility of this design, we instantiate EdgeKernelBench with TVM as the reference compiler stack (Chen et al., 2018). We evaluate five LLMs on 650 task instances across CPU/L-LVM, GPU/CUDA, and GPU/OpenCL execution paths. The results show that a consistent workflow for generation, validation, and measurement runs across heterogeneous backends. The hierarchical benchmark also reveals how the model capability changes as the program scope grows. The experiments also expose the limits of one-shot generation. Across 650 task instances, the strongest model achieves 73.5% Compile@1 and 64.5% Correct@1, but only 25.5% Fast@1 .0.At Level 3, the highest Fast@1 .0 scores on the three backends fall further to values between 0.0% and 4.0%. As the program scope grows, one-shot generation struggles to coordinate increasingly coupled decisions across representation levels. To address this limitation, we further introduce LEKA , the Layered Edge Kernel Agent. LEKA decomposes coupled cross-level decisions along the IR hierarchy, allowing each agent to focus on one representation while preserving coordination across levels. On a randomly sampled 69-instance subset for agent evaluation, LEKA raises Correct@1 from 42.0% to 100.0% and Fast@1 .0 from 13.0% to 43.5% relative to one-shot generation. With the same base model, task contract, and wall-clock budget, LEKA raises Fast@1 .0 from 26.1% for the pure Claude Code baseline to 43.5%. 2Preprint. Our work makes three contributions. • We introduce EdgeKernelBench, which combines a unified IR deployment framework with a hierarchical benchmark for edge workloads. It provides a common basis for studying LLM kernel generation and optimization on edge devices. • We introduce LEKA, a general agent architecture for edge kernel generation and opti-mization. LEKA organizes optimization through a layered IR to reduce the complexity of decisions across representation levels. • We conduct systematic experiments on a range of representative edge hardware backends. The evaluation measures the edge kernel generation capabilities of leading LLMs and ex-amines their main failure modes. It also tests the optimization gains from LEKA. 

## 2 RELATED WORK 

Kernel generation benchmarks. Benchmarks have spread from server GPUs to NPUs, TPUs, and multi-vendor accelerators (Wen et al., 2026; Cao et al., 2026; Zang et al., 2026), but the hardware stays largely server-class, the tasks stay server-oriented, and the artifact stays native code (Yu et al., 2026). One benchmark reaches mobile devices, and it covers mainly single operators and their attribute variants (Zou et al., 2026). Native code leaves the model to meet each backend’s language and legality rules itself, so correctness collapses on hardware it has rarely seen (Wen et al., 2026; Zang et al., 2026). These benchmarks mostly share the KernelBench protocol, which organizes PyTorch reference programs by scope and scores generated kernels on correctness and speedup over a software baseline (Ouyang et al., 2025). EdgeKernelBench keeps the protocol but evaluates on heterogeneous edge backends, draws its tasks from edge applications, spans single operators to compact model graphs, and replaces native code with one IR shared by all backends. 

Compilers and portable kernel representations. Deployment stacks fix their optimization knowledge in expert-written kernels or schedule rules, whereas LLM generators hold such knowl-edge but emit native code and forgo the portability a compiler provides. Inference engines ship a hand-written kernel for each operator and backend (Jiang et al., 2020; David et al., 2021; NVIDIA, 2026). Tensor compilers lower one program through several IR levels to many backends (Chen et al., 2018; Lai et al., 2025; Lattner et al., 2021) and search a rule-defined schedule space with cost mod-els and hundreds to thousands of on-device measurements (Zheng et al., 2020; Shao et al., 2022). Neither can reach a transformation outside its encoding, such as an algebraic rewrite or an unfore-seen fusion boundary. EdgeKernelBench puts the LLM’s computation, scheduling, and memory decisions in a unified IR that a deterministic backend adapter lowers to each backend. 

LLM-driven kernel optimization. Methods beyond one-shot generation differ in where they spend compute but most treat one native program as the unit of optimization. Training-time methods fine-tune a model with execution rewards until it specializes in one kernel language (Baronio et al., 2026; Bai et al., 2026; Li et al., 2025b; Cao et al., 2026). Inference-time methods keep the model fixed and iterate through agent roles with profiler feedback (Wei et al., 2025; Zhang et al., 2025), evolutionary search over a candidate lineage (Chen et al., 2026), repair loops inside a mobile frame-work (Zou et al., 2026), or a generate-test-refine loop over a kernel abstraction layer (Saba et al., 2026). That unit entangles algorithm, fusion, thread-mapping, and instruction choices, so a reward scores the whole program and a profile points at a slow kernel, not at the decision level behind it. LEKA gives each IR level its own agent and routes every measurement to the level that owns the decision rather than to the whole program.

Organization along two dimensions. EdgeKernelBench contains 331 canonical tasks organized along two orthogonal dimensions. The first dimension captures compositional complexity. Level 1 Basic Compute Patterns contains 128 basic operators or core computation patterns. The second dimension groups tasks by edge application. It includes Mobile and Personal Intelligence with 204 instances, Smart AIoT with 228, and Embodied Robotics with 218. Each domain spans all three complexity levels. Every task corresponds to a meaningful model structure from an edge application. Correctness and performance gains on these tasks therefore indicate potential value for practical edge deployment. 3.2 UNIFIED GENERATION AND EVALUATION FRAMEWORK 

Shared representation. Edge deployment spans fragmented software stacks and must meet strict resource limits. Program generation must therefore accommodate different backends while balanc-ing execution performance against memory use. EdgeKernelBench separates the shared task and evaluation contract from the deployment implementation for each backend. Given a PyTorch refer-ence program and a description of the target device, the LLM expresses its optimization decisions in Unified Kernel IR . The IR places computation, scheduling, and memory in a shared optimization space while preserving target-specific choices. Backend adapters lower the shared IR into target-specific executable programs. This separation makes optimization intent reusable across edge de-vices and software stacks. New backends can join the same generation and evaluation workflow through dedicated adapters without changing the shared task contract or evaluation protocol. 

Unified evaluation pipeline. EdgeKernelBench provides a unified evaluation of LLM-generated edge kernels across heterogeneous backends. The protocol proceeds through candidate construction, functional validation, and performance measurement. These stages reveal deployability and locate failures throughout the process. The evaluation characterizes each candidate by its compilation success, functional correctness, and execution performance. ## 4 LAYERED EDGE KERNEL AGENT (LEKA) 

EdgeKernelBench provides a unified generation and evaluation interface, yet one LLM call must coordinate decisions across several abstraction levels. For complex tasks, a single agent must re-tain a global view of the computation graph while reasoning about implementation details at lower levels within a limited context. As program scope grows, this context burden constrains optimiza-tion and makes execution feedback harder to attribute. We therefore introduce the Layered Edge 

Kernel Agent, or LEKA . As shown in Figure 3, LEKA decomposes optimization by IR level. A shared candidate tree links decisions across levels and gives each layer agent a focused view of the optimization space exposed at its IR level, while hardware feedback drives subsequent iterations. 4.1 HIERARCHICAL IR O PTIMIZATION

Progressive lowering and focused context. LEKA follows progressive lowering across multiple IR levels (Lattner et al., 2021). As lowering proceeds, decisions made at upper levels gradually become fixed while finer optimization spaces open. This order lets each decision be optimized at the IR level that expresses it most directly. The scope of each agent narrows in parallel from the full program to local implementation details. Compared with a single agent that must retain both global program structure and low-level details in the same context, LEKA decomposes a complex task 5Preprint. into optimization steps aligned with individual IR levels. This decomposition reduces the context required by each call and makes execution feedback easier to attribute to the relevant level. 

Shared abstractions and target specialization. LEKA first searches EdgeKernelBench’s backend-shared IR layers, each covering optimization at a different program granularity. During target-specific lowering, the adapter retains high-level optimizations and exposes more hardware-coupled choices to lower-level agents. This separation allows LEKA to transfer high-level optimizations to new backends and focus the remaining adaptation search on target-specific implementation details. 4.2 CANDIDATE SEARCH GUIDED BY EVIDENCE 

Candidate search with lineage tracking. LEKA organizes its feedback loop as a lineage search over the candidate tree introduced above (Yin et al., 2025). With every optimization attempt, LEKA adds a new state while retaining earlier candidates and their validation results. The orange path in Figure 3 marks the active optimization trajectory, while the remaining branches preserve alterna-tives for comparison, rollback, or continued search. Each layer agent expands candidates within its assigned optimization space, and the shared tree connects these local searches across IR levels. 

Feedback from hardware evidence. For each executable candidate vt, the hardware-sensing agent runs the evaluator on the target device and collects detailed feedback. It uses these measurements to identify the level ℓt that needs further optimization and writes a report rt for the candidate. The selected layer agent uses the report attached to the node to generate the next candidate, forming a layered iteration driven by device measurements. 

## 5 EXPERIMENTS 

5.1 EXPERIMENTAL SETUP 

Evaluation environment. We instantiate EdgeKernelBench and LEKA with TVM 0.23.0 1 (Chen et al., 2018), chosen for its mature open-source ecosystem and established use in practice. Through a modified TVM integration, EdgeKernelBench manages task construction, device descriptions, and the optimization workflow. LEKA optimizes computation graphs in Relax and computation and scheduling in TIR. It refines implementations in CUDA C (NVIDIA, 2024), OpenCL C (Khronos Group, n.d.), or LLVM IR (Lattner & Adve, 2004). All optimization decisions come from the LLM or agent. TVM handles representation conversion, target code generation, and runtime support. We evaluate three devices to cover different edge hardware and software ecosystems. CPU/LLVM runs on an iQOO Neo9S Pro+ with a Snapdragon 8 Gen 3 SoC. The GPU/CUDA device is an NVIDIA Jetson AGX Orin 64GB. For GPU/OpenCL, we use a Firefly ROC-RK3588S-PC with a Mali-G610 GPU. We evaluate compilation, correctness, and performance on each device. 

Metrics. We report compilation success rate (CSR, Compile@1), functional correctness rate (FCR, Correct@1), Fast@ p, and geometric mean speedup (GM). CSR is the fraction of tasks whose gen-erated programs compile successfully. FCR additionally requires all output checks to pass. Fast@ p

is the fraction of tasks with correct programs, valid timings, and a median paired speedup above p

over the baseline (Ouyang et al., 2025). GM is the geometric mean of speedups over the specified baseline for valid programs on the same task set, including slower results. 

Evaluation tasks and models. Following the EdgeKernelBench configuration, CPU/LLVM uses tasks from Mobile and Personal Intelligence, GPU/CUDA from Embodied Robotics, and GPU/OpenCL from Smart AIoT. We adapt input shapes to each scenario and retain all three com-plexity levels. Our one-shot evaluation covers representative proprietary models, including GPT-5.6-sol (OpenAI, 2026), Gemini-3.7-Flash (Google, 2026), and Claude Sonnet 5 (Anthropic, 2026). We also evaluate the open-weight models DeepSeek-V4-Pro-0813 (abbreviated as DeepSeek-V4-Pro) (DeepSeek-AI, 2026) and GLM-5.3 (Z.ai, 2026a). Given time constraints, we use stratified random sampling by complexity level to select 69 task instances across the three backends for LEKA evalu-ation. LEKA and the pure Claude Code baseline both use GLM-5.3-Flash (Z.ai, 2026b) as the base model. They share the same task contracts, evaluator, and time budgets.

5.2 BASELINE EVALUATION 

5.2.1 COMPILER -B ASELINE RESULTS 

We use the TVM compilation pipeline tuned with MetaSchedule as the baseline. We evaluate com-pilation success, functional correctness, and execution performance under one-shot generation. Ta-ble 1 shows how generation quality varies with task complexity, hardware backend, and model. Across task levels, CSR, FCR, and F@1 generally decline as tasks expand from single operators to operator compositions and multi-module computation graphs. Across the three backends, the highest F@1 falls from 51.0% at Level 1 to 16.2% at Level 2 and 4.0% at Level 3. More complex tasks introduce longer semantic dependency chains. They also require models to coordinate computation and storage across a larger program context. These demands make it harder to maintain program consistency and optimize across operators. As a result, generation capabilities on basic operators do not readily extend to complex computation graphs. Hardware backends also affect generation quality, with generally higher FCR on CPU than on GPU. At Level 1, the highest FCR reaches 94.5% on CPU, compared with 79.6% on CUDA and 73.5% on OpenCL. Thread partitioning and parallel mapping make valid GPU implementations harder to generate. Across the two GPU configurations, CUDA achieves higher F@1 overall. The advantage is most consistent at Level 1, where every model outperforms its OpenCL result. We hypothesize that this partly reflects greater exposure to high-quality CUDA implementations during training. Models also differ in their strengths. Among proprietary models, GPT maintains relatively high F@1 across multiple backends. Gemini performs well on complex tasks, achieving the highest Level 3 FCR on all three backends. Among open-weight models, DeepSeek achieves strong correctness on CPU, reaching 75.3% FCR at Level 2. Its corresponding F@1 is only 3.2%, compared with 15.1% for GPT. Open-weight models can therefore exceed proprietary models in correctness under some configurations, while still trailing in execution performance. Model strengths in program correctness do not necessarily carry over to performance optimization. 5.2.2 PRODUCTION -I NFERENCE -E NGINE RESULTS

## 6 CONCLUSION 

Fragmented hardware and software ecosystems make it harder for LLMs to adapt and optimize kernels for resource-constrained edge devices. We introduce EdgeKernelBench, which combines a unified IR deployment framework with a hierarchical benchmark. It provides a common foundation for kernel generation, deployment, and evaluation across heterogeneous edge backends. We also introduce LEKA, which organizes optimization search across IR levels and uses device feedback to refine candidate programs. Our evaluation shows that model optimization performance varies with program complexity and target hardware. LEKA outperforms the compiler baseline on more tasks than direct generation or a budget-matched general coding agent across the evaluated backends. These findings also offer a perspective on how optimization responsibilities are divided between models and compilers. Lower-level program representations give models more direct control over hardware but introduce more complex constraints and decisions. As models become more capable, an open question is whether this boundary can shift toward lower levels. A related question is how to define layer boundaries and design IRs that help agents reason about optimization choices and constraints. EdgeKernelBench and LEKA provide an experimental foundation for studying this relationship between model capability, program abstraction, and optimization freedom. 9Preprint.

We check each generated program against its PyTorch reference using inputs drawn from three ran-dom seeds. Correctness requires matching output structures, shapes, and data types, with numerical differences within the task-specific tolerance. Only programs that pass these checks proceed to performance evaluation. Our paired evaluation protocol measures candidate and baseline programs in the same device session with identical inputs and matched execution settings. Timing covers one complete execution of the task, with inputs already placed on the target device. Compilation and deployment-time preparation are excluded, while computation that depends on dynamic inputs remains within the timed execu-tion. Candidate and baseline programs use the same timing boundary within each comparison. For comparisons against TensorRT, CUDA events measure device-side latency. GPU measurements use explicit synchronization to account for execution completion. Both programs are warmed up before repeated measurement, with warm-up settings matched within each backend. For CPU evaluation, we keep worker threads on designated cores and repeat each execution to improve timing consistency. We use the robust coefficient of variation (rCV) to assess the stability of repeated measurements. ## C BASELINE CONSTRUCTION AND FAIRNESS CONTROLS 

C.1 TVM C OMPILER BASELINE 

Budgeted compiler reference. We construct the TVM baseline by importing each PyTorch ref-erence and extracting the optimization tasks for MetaSchedule. Before evaluation, we search and measure candidate schedules on the target hardware using the convergence-calibrated budgets de-scribed below. The resulting tuning database stores the schedules and their measured latencies for each workload and target. We build the baseline from the lowest-latency valid schedule found for the matching workload and target within this search budget. 

Backend-specific calibration. A benchmark task may yield multiple MetaSchedule tuning tasks, each corresponding to a PrimFunc exposed after graph lowering and fusion. Since convolution, matrix multiplication, reduction, and elementwise programs induce substantially different search spaces, a single fixed trial count would allocate the same cost to tasks with very different scheduling difficulty. ## D UNIFIED IR AND DEPLOYMENT FRAMEWORK 

Section 3.2 introduces the shared representation and evaluation pipeline. Here we describe the optimization scope, generation contract, and compiler integration. D.1 UNIFIED IR AND OPTIMIZATION SCOPE 

Unified Kernel IR describes deployment programs at two complementary levels. The graph and invocation level expresses computational dependencies, fusion boundaries, and the flow of interme-diate results. The computation and scheduling level specifies loops, data layouts, memory accesses, and parallel mappings. Together, these levels let the model coordinate local kernel changes with the organization of the surrounding program. Memory decisions span both levels. Fusion and decomposition determine which intermediate ten-sors are materialized and how long they remain live. Local scheduling determines data reuse and temporary storage within each computation. Exposing these choices allows the model to weigh exe-cution latency against memory use under the target device’s resource constraints. The representation accommodates different parallel strategies and storage organizations for different targets. D.2 GENERATION CONTRACT AND PROGRAM CONSTRUCTION 

The PyTorch reference defines the computation, while input and output specifications and numerical tolerances define the program’s observable behavior. Within this contract, the LLM can reorganize computations, intermediate layouts, fusion boundaries, and execution schedules. These choices preserve the task interface while allowing different implementations of the same computation. The framework builds an executable program from the generated artifact and checks its structure and compatibility with the target backend. Numerical validation then verifies that its outputs agree with the PyTorch reference within the specified tolerances. D.3 COMPILER INTEGRATION AND BACKEND DEPLOYMENT 

Progressive lowering converts the representation into an executable artifact through compiler trans-formations. These transformations resolve storage and execution details under the backend’s con-straints. The deployment path loads the artifact and binds its entry point to the runtime interface. Our implementation uses TVM’s layered IR, code generation, and runtime support for program construction and device execution. Within this pipeline, EdgeKernelBench provides task and gener-18 Preprint. ation interfaces through which LLMs optimize operator implementations, then passes the programs to the evaluator. Backend integration lowers LLM-generated programs from the unified IR to the target backend without introducing additional optimization. The lowered programs follow compila-tion and runtime paths for CPU/LLVM, GPU/CUDA, or GPU/OpenCL. These components provide backend integration and runtime support for the generated programs. D.4 COMPILER INSTANTIATION AND HARDWARE ADAPTATION 

When instantiating EdgeKernelBench with a new compiler, we implement the unified generation interface using that compiler’s IR. The LLM then writes operator implementations and expresses optimization decisions in this representation. Compiler adapters connect the generated programs to the corresponding lowering, code generation, and runtime paths. For new hardware supported by the compiler, we extend the target configuration and deployment adapter to connect to the device runtime. These extensions retain the same task definitions and evaluation criteria.

E.2.1 ONE -SHOT GENERATION CASE STUDIES 

We examine two one-shot implementations through generated code and paired measurements fol-lowing the protocol in Appendix B. 

Selective fusion and intermediate storage. On the OpenCL ConvNeXt block, Gemini-3.7-Flash reduces latency from 18.0 ms to 0.6 ms, achieving a 30 .9× speedup over TVM. The implementation uses separate kernels for depthwise convolution and channel transformations to accommodate their different memory access patterns. The convolution kernel reuses spatial neighborhoods in work-group memory and writes its output in the layout required by the next stage. The second kernel fuses normalization, two linear transformations, activation, and the residual connection. It avoids writing the full expanded hidden activation to global memory. For this task, GPT-5.6-sol generates one kernel that fuses the entire block. Its implementation tiles the hidden channels and repeatedly synchronizes the workgroup between tile computations. It achieves only 0.9× the performance of its corresponding TVM baseline. This comparison suggests that extensive fusion does not necessarily yield better performance. Separating stages with different access patterns can improve data reuse and reduce synchronization overhead, even when it introduces an intermediate tensor. 

Joint optimization of dequantization and matrix multiplication. On the CPU dequantization and matrix multiplication task, Gemini-3.7-Flash reduces latency from 39.7 ms with MNN to 2.1 ms. The paired speedup is 19 .0×. The reference program converts integer weights to floating point, ap-plies zero points and scales, and then performs matrix multiplication. The generated implementation reuses the reference program’s integer weights and per-channel quantization parameters. It moves zero-point correction and scaling after the reduction, reading integer weights directly for floating-point accumulation. This rearrangement avoids creating and storing the entire weight matrix in floating-point form. The implementation parallelizes blocks of output channels and uses vectorized loops to access contiguous weights and accumulate outputs. For the 2048 × 5632 weight matrix, it avoids a 44 MiB floating-point intermediate. The case illustrates how algebraic rearrangement can reduce both intermediate storage and elementwise work within the reduction. E.2.2 LEKA O PTIMIZATION CASE STUDIES 

We trace two LEKA runs with GLM-5.3-Flash to examine how optimization proceeds across pro-gram layers. The final implementations are compared against the tuned TVM baselines using the evaluation protocol in Appendix B. 

From graph rewrites to device-level refinement. On the CUDA task combining batched matrix multiplication, instance normalization, addition, and multiplication, LEKA achieves a latency of 16.2 μs in formal evaluation. The final implementation achieves a 1.2× speedup over the tuned TVM baseline at 19.8 μs. This computation mixes matrix arithmetic and reductions with short elementwise operations, leaving optimization opportunities at several program layers. L0 first fuses the final elementwise operations. It uses the parameter preparation mechanism to move fixed-weight layout conversion and normalization constant preparation outside the repeated infer-ence call. Given the weight layout, L1 fuses matrix multiplication with bias addition and reschedules the matrix computation and normalization reduction. These changes reduce the search-stage latency of this branch from approximately 104.0 μs to 20.0 μs. L2 redistributes work within thread blocks to avoid duplicate weight loads and uses vectorized accesses and register reuse to reduce memory traffic. Warp-level reductions also reduce block-wide synchronization in the normalization kernel from eight barriers to one. The resulting implementation runs in approximately 16.2 μs. The trajectory reveals dependencies between decisions. The graph layer establishes the parameter layout and computation boundaries that the scheduling layer uses to organize parallel work. After an upstream change, LEKA rebuilds the affected downstream implementations and retains the best verified complete program. This preserves compatible improvements as search moves between layers. 

Hardware feedback directs schedule refinement. On the CPU task combining convolution with addition, scaling, sigmoid, and group normalization, LEKA reaches 17.0 ms in formal evaluation. This is a 1.6× speedup over the TVM baseline at 27.5 ms. Although the graph contains several elementwise and reduction stages, convolution still accounts for approximately 85.0% of the profiled interval after the first effective scheduling pass. This evidence directs further optimization toward data reuse and register blocking in the convolution. L1 constructs a convolution microkernel that computes several output channels and adjacent spatial positions together. It retains accumulations in registers and uses loop unrolling and vectorization to reuse inputs. This optimization reduces the search-stage latency to 19.7 ms. With profiling showing that convolution remains dominant, L1 expands the microtile from eight output channels by four spatial positions to eight channels by eight positions. The wider spatial tile amortizes each weight load over more multiply-accumulate operations while keeping the accumulators within the register budget. This refinement lowers the search-stage latency to approximately 17.0 ms. Hardware feedback identifies the dominant computation, and L1 refines its loops while preserving the graph and call interfaces. The implementation preserves the L0 graph and achieves its gains through L1 scheduling without further L2 code changes. The case illustrates how the layered design supports sustained optimization within the layer that contains the measured bottleneck.

## G LIMITATIONS AND FUTURE WORK 

G.1 LIMITATIONS 

Our evaluation covers CPU/LLVM, GPU/CUDA, and GPU/OpenCL, but does not yet include spe-cialized accelerators such as NPUs. We evaluate each task on a CPU or a GPU separately, without partitioning its computation between the two for cooperative execution. Such settings involve task allocation and resource sharing across compute units and would broaden the evaluation scope. G.2 FUTURE WORK 

Future work could explore how the organization of the unified IR supports focused agent reasoning and coordinated optimization. Using multilevel compiler infrastructure such as the MLIR-based 24 Preprint. IREE, 4 EdgeKernelBench could expose finer-grained representations for optimization and support different divisions of work among agents. Comparing layer boundaries, context sharing, and cross-layer feedback would help identify how to narrow each agent’s search space while retaining oppor-tunities to jointly optimize computation, memory use, and scheduling. Extending the evaluation to NPUs would enable research on program optimization under specialized compute and on-chip memory constraints. For CPUs and GPUs within the same device, we could jointly optimize computation partitioning, data transfers, and synchronization for a single task. This would allow us to examine how the benefits of heterogeneous execution vary with workloads and resource budgets, and to explore trade-offs between performance and memory use.
