## 摘要
诸如 Arm SVE 的可扩展向量指令集支持向量长度无关（VLA）执行，使单一实现能够适应具有不同向量长度的硬件。然而，它们使编译器代码生成变得复杂，因为分块和数据布局决策无法再在编译时固定。我们提出了一种方法，通过向量长度感知的打包数据布局及相应的编译器扩展，在端到端机器学习编译流水线中实现 VLA 代码生成。我们将这些机制集成到 MLIR/IREE 中，并扩展分块、融合和向量化以支持可扩展向量长度。在 Arm CPU 上的真实机器学习工作负载上评估，我们的方法生成的 SVE 代码与 IREE 中现有的基于 NEON 的代码生成具有竞争力，且通常优于后者，实现了高达 1.45 倍的加速。我们还优于 PyTorch 生态系统框架，包括 ExecuTorch、TorchInductor 和即时执行，展示了可扩展向量化在生产编译器环境中的有效性。基于模拟器的研究进一步表明，生成的代码在计算密集型工作负载上随 SVE 向量长度增加而扩展，支持跨硬件配置的性能可移植性。

## Abstract
Scalable vector instruction sets such as Arm SVE enable vector-length-agnostic (VLA) execution, allowing a single implementation to adapt across hardware with different vector lengths. However, they complicate compiler code generation, as tiling and data layout decisions can no longer be fixed at compile time. We present an approach for enabling VLA code generation in an end-to-end ML compilation pipeline through vector-length-aware packed data layouts and corresponding compiler extensions. We integrate these mechanisms into MLIR/IREE and extend tiling, fusion, and vectorization to operate with scalable vector lengths. Evaluated on real-world ML workloads on Arm CPUs, our approach generates SVE code that is competitive with, and often outperforms, existing NEON-based code generation within IREE, achieving up to $1.45\times$ speedup. We also outperform PyTorch ecosystem frameworks, including ExecuTorch, TorchInductor, and eager execution, demonstrating the effectiveness of scalable vectorization in a production compiler setting. A simulator-based study further shows that the generated code scales with increasing SVE vector length on compute-bound workloads, supporting performance portability across hardware configurations.

## 1. 核心问题与整体含义（研究动机与背景）

- **背景**：ML 工作负载需在多样化 CPU 硬件上部署，且往往要求"一次编译、多代硬件运行"，避免逐设备重编译。现代 CPU 依赖 SIMD 扩展（如 Arm NEON，固定 128 位）来挖掘数据级并行，但固定向量长度意味着跨不同向量长度硬件需重新调优。
- **新范式**：Arm SVE 等可伸缩向量指令集引入**向量长度无关（VLA）**编程模型，向量长度在 128–2048 位间由硬件实现决定、运行时才确定，单一二进制可跨硬件适配，兼顾性能可移植性。
- **核心矛盾**：VLA 给编译器代码生成带来根本困难——**分块（tiling）与数据布局决策无法在编译期固定**。传统高性能矩阵乘依赖"打包（packed）布局"，其 tile 尺寸通常按目标向量长度设为编译期常量；在 SVE 下向量长度未知，这一前提失效。
- **现有差距**：主流端到端 ML 编译器（MLIR/IREE 等）主要围绕定长向量化设计；已有 VLA 编译器工作（如 TVM 的 SVE/SME 集成、RVV 的 MetaSchedule 方案）多通过循环变换或自动调优表达向量长度依赖，**未将数据打包/布局作为一等抽象**，向量长度无关性仅停留在执行层而非数据表示层。
- **论文目标**：在端到端 ML 编译流水线中实现 VLA 代码生成，使数据布局与计算同时随硬件向量长度自适应，且无需逐实现重调优。

## 2. 方法论

### 2.1 核心思想
提出**可伸缩打包布局（scalable packed layouts）**：将打包 tile 尺寸表达为硬件向量长度 \(V_L\) 的函数，而非编译期常量，使同一布局与内核设计可跨不同向量长度硬件适配。

### 2.2 关键技术细节

- **打包矩阵乘形式化**：对行主序 \(A \in \mathbb{R}^{M\times K}\)，按微内核 tile 形状 \((m_r, k_r)\) 重排为高阶张量
  \(A_{pack} \in \mathbb{R}^{\lceil M/m_r\rceil \times \lceil K/k_r\rceil \times m_r \times k_r}\)，
  索引关系 \(A_{pack}[i_o,k_o,i_i,k_i] = A[i_o m_r + i_i,\ k_o k_r + k_i]\)。\(B\)、\(C\) 同理按 \((k_r,n_r)\)、\((m_r,n_r)\) 打包。打包是显式数据变换（物化到内存），而非逻辑视图。
- **可伸缩化**：将 tile 尺寸写成 \(m_r=f_m(V_L),\ n_r=f_n(V_L),\ k_r=f_k(V_L)\)，具体函数形式由微内核的指令级访问模式与展开策略决定。布局须保证微内核每次迭代消费的操作数块在内存中连续。
- **代表性微内核**：给出一个 FP32 SVE 外积形式内核（8 × 2\(V_L\) 输出 tile），每步沿 K 维消费 A 的 8×1 切片（两组 4 元素，经 `svld1rq` 复制到向量寄存器）与 B 的 1×2\(V_L\) 切片（两条长度 \(V_L\) 的连续向量加载），用 `svmla_lane` 做 lane 级乘加，共 16 个累加寄存器。
- **通用性论证**：不同 ISA/数据类型诱导不同 \((f_m,f_n,f_k)\)，但构造方式一致；该形式化不限制传统打包布局的设计空间（不同 tiling 策略、内核形状、局部性权衡均可通过这三个函数表达）。

### 2.3 编译器实现（MLIR/IREE）

- **数据分块表述**：沿用 IREE 已有的 `linalg.pack` → `linalg.mmt4d` → `linalg.unpack` 三阶段分解，将其 tile 尺寸改为 \(V_L\) 的函数；与 BLAS 类"内核内即时打包 + 缓存级分块"不同，这里把打包作为**显式操作**物化，便于组合与跨融合传播。
- **布局与内核生成**：编译器从面向目标硬件特性与数据类型的预定义布局配置中选取微内核结构（如外积形式）及其布局，据此生成打包变换与向量化计算；外围循环、高层分块、融合、向量化、bufferization 由编译器启发式自动决定。
- **融合与布局传播**：pack/unpack 可融合进矩阵乘的生产者/消费者，或跨相邻算子传播以摊薄打包开销；相应扩展了 MLIR/IREE 的 tiling、fusion、vectorization pass，使其在 tile 尺寸选择、循环融合、向量化时感知可伸缩布局，保证子图变换与目标微内核布局一致。
- **填充语义与向量化**：打包布局天然含 padding（按上取整维度定义 tile），当寄存器级 tile 尺寸与布局对齐时可免去额外掩码；扩展 linalg 向量化机制以支持 scalable vector 类型与 tile 尺寸，使向量化器能推理张量动态形状与可伸缩向量表示的对应关系，避免引入多余掩码。
- **可扩展性**：只要向量操作到目标指令的 lowering 受支持，即可推广到其他数据类型（BF16、INT8）与其他可伸缩 ISA（RVV、Arm SME）。

## 6. 主要结论与发现

- **对 IREE (NEON)**：Orion O6 上 11 个模型中 7 个更优（最高 1.33×），Pixel 9 上 9 个中 5 个更优（最高 1.45×）。由于两平台 SVE 与 NEON 向量长度相同，差异源于代码生成策略与布局：SVE 的一等谓词寄存器与专用循环控制指令（如 WHILELT）消除 NEON 典型的标量收尾循环与分支密集尾声；编译器在向量长度未知时做出的不同 tiling/调度决策在某些负载（尤其多线程）下更有利。反之，可伸缩向量类型在编译期不透明，可能妨碍对齐推断并引入保守谓词掩码，最坏造成 27% 性能损失。
- **对 ExecuTorch**：Orion O6 上 11 个中 8 个更优（最高 1.70×），Pixel 9 上 9/9 全胜（最高 12.38×）；增益集中在矩阵乘主导的 Transformer/注意力负载。卷积主导模型（Whisper-Base、AST、YOLOS-Tiny）落后，因缺少卷积直接 data-tiling，经 im2col 物化大中间矩阵。
- **对 PyTorch 生态**：优于 eager 8/11（最高 3.67×）、优于 TorchInductor 9/11（最高 6.09×）；作者谨慎指出这反映 Inductor CPU 后端在多样 Arm 平台上泛化不足，而非普遍结论（其在 Graviton3 上经调优表现良好）。
- **模拟器缩放**：缓存驻留 matmul 近理想扩展——1024³ 在 SVE-512 达 3.36×，skinny-K 达 3.44×（理想上限 4×，差距来自更宽向量的水平归约延迟）；N=2048 时因 48MiB 操作数远超 8MiB L3 转为访存受限，SVE-512 仅 1.29×，L3 增至 16MiB 后恢复至 3.32×。SmolLM2-135M 端到端在 SVE-256/512 分别 1.46×/1.82×，受限于未覆盖的访存受限非 matmul 算子（softmax、LayerNorm、逐元素）。
- **总体判断**：可伸缩向量化可集成进生产级编译器栈，在保持高性能的同时获得跨硬件代际的可移植性。

## 7. 优点

- **抽象层面的创新**：把向量长度无关性**编码进数据布局本身**（tile 尺寸为 \(V_L\) 的函数），而非仅靠循环变换或逐实现自动调优，使布局驱动优化可贯穿整条编译流水线。
- **工程落地性强**：集成于生产级 MLIR/IREE，扩展 tiling/fusion/vectorization/bufferization 全链路，代码由编译器自动生成而非手写内核；开源并推进上游合入。
- **对比设计严谨**：同栈 NEON vs SVE 隔离变量；基线取最优线程配置；明确指出两平台向量长度相同、差异不可归因于向量长度，避免过度解读。
- **补充模拟器研究**：在真机无法体现向量长度差异的现实约束下，用受控 gem5 实验隔离向量长度效应，并诚实分析访存受限拐点与理想上限差距来源。
- **自我批判充分**：主动讨论可伸缩类型不透明导致的掩码/对齐惩罚、卷积经 im2col 的劣势、SME 上向量指令无缩放收益等反例。

## 8. 不足与局限

- **真机验证缺口**：两平台 SVE 均为 128 位，性能可移植性这一核心主张仅由模拟器支撑；作者亦指出 Graviton3（256 位）因 SVE 执行单元少于 NEON 而吞吐相当，Snapdragon 8 Elite Gen 5（512 位 SVL）与 Apple M4 类处理器上向量指令无清晰缩放，说明向量长度并非性能决定因素，微架构可主导结果。
- **算子覆盖窄**：打包布局与变换仅针对矩阵乘；卷积经 im2col 复用同一策略，带来额外开销，导致卷积主导模型（Whisper、AST、YOLOS）落后于库式方案。
